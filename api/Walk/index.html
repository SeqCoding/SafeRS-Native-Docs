    Walk¶

    srs::api::Walk / srs.walk + game.* aliases

    Navigation API covering full pathfinding, single-tile clicks, and safe-tile selection. The same C++ surface is exposed both as srs::api::Walk and on the Lua game.* table for short, readable script call sites.

    All calls are safe no-ops (returning false / true depending on intent) when the executor isn't wired (pre-init host).

    Method C++ Lua
    Path-routed walk (hybrid) Walk::to(ctx, x, y, useTransports=true) → bool srs.walk.to(x, y, useTransports?) → bool
    game.moveTo(x, y[, useTransports]) → bool
    Path-routed canvas walk — game.walkTo(x, y[, useTransports]) → bool
    Path-routed minimap walk — game.minimapWalkTo(x, y[, useTransports]) → bool
    Single-click canvas walk Walk::fastCanvas(ctx, x, y, plane=-1) → bool game.walkFastCanvas(x, y[, plane]) → bool
    Smart auto-dispatch Walk::walkSmart(ctx, x, y, plane=-1) → bool game.walkSmart(x, y[, plane]) → bool
    Find a safe walkable tile Walk::findSafeTile(ctx, originX, originY, danger, radius, plane=-1) → SafeTile game.findSafeTile(originX, originY, danger[, radius[, plane]]) → table \| nil
    Stop walking Walk::cancel(ctx) srs.walk.cancel() / game.cancelMove()
    Currently walking Walk::isMoving(ctx) → bool srs.walk.isMoving() / game.isMoving() → bool
    At goal Walk::hasArrived(ctx) → bool srs.walk.hasArrived() / game.hasArrived() → bool
    Tile walkable? — game.isWalkable(x, y) → bool

    Which dispatch should I use?¶

    Scenario Use
    Long-distance navigation, may need transports/multi-leg srs.walk.to / game.moveTo
    Force minimap clicks (long-haul behavior even close-up) game.minimapWalkTo
    Force canvas clicks throughout the path game.walkTo
    Short, time-critical dodge (1–2 ticks, single tile) game.walkFastCanvas
    "Just get me there, I don't care how" game.walkSmart
    Pick the closest safe tile, then walk there game.findSafeTile + game.walkSmart

    walkFastCanvas — single-click, no client pathfinding¶

    Fires one canvas "Walk here" click at the destination tile and returns immediately. The OSRS server resolves the route, the client does no A*.

    Use this for short, time-critical movements where you need a single click to fire on the current tick (dodging a falling-rocks tile, side-stepping a tick-attack hitbox).

    Behavior:

    • Returns false if the tile is off-viewport (the engine can't click what it can't see). Camera angle matters — tiles behind the player or above the screen edge don't project.
    • No path validation. If a wall sits between you and the target, the server walks around it (or refuses); the client has no opinion.
    • No arrival polling. It's fire-and-forget. Re-check srs.player.position() next tick if you need to confirm.
    • plane defaults to the player's current plane.
    -- Side-step east by one tile, immediately.
local p = srs.player.position()
game.walkFastCanvas(p.x + 1, p.y, p.plane)

    walkSmart — automatic dispatch¶

    Picks walkFastCanvas if the target tile projects onto the canvas, otherwise falls back to the hybrid path executor (Walk::to).

    -- Caller doesn't need to know whether the tile is visible.
game.walkSmart(targetX, targetY)

    Returns true if a walk was dispatched. Useful when you have a target tile from some computation (findSafeTile, a script's own planning, etc.) and don't care which dispatch path is used.

    findSafeTile — pick the closest walkable tile not in danger¶

    Searches outward by Chebyshev distance from (originX, originY) for the closest tile that satisfies all of:

    1. Not in the dangerTiles list (plane-aware match).
    2. Walkable according to the live collision map.
    3. Preferably on the current canvas (one-click reachable).

    The origin tile itself is skipped — call this when the origin is the problem. If multiple candidates tie on distance, on-canvas tiles win (so the result can usually be reached via walkFastCanvas). If the search exhausts without finding any on-canvas safe tile, the closest off-canvas safe tile is returned (so walkSmart can fall back to the path executor for the multi-tick approach).

    Arguments:

    Arg Default Notes
    originX, originY — Where to search around (usually the player's current tile).
    dangerTiles — List of {x=, y=, plane=} tables. plane defaults to the search plane if omitted.
    radius 5 Search radius in tiles (Chebyshev). Capped at 32.
    plane -1 Search plane. -1 uses the player's current plane.

    Returns (Lua):

    { x=…, y=…, plane=…, onCanvas=true|false, walkable=true }

    or nil if nothing in range qualifies.

    local p = srs.player.position()
local danger = { {x=p.x, y=p.y, plane=p.plane} }  -- I'm standing on it
local safe = game.findSafeTile(p.x, p.y, danger, 3)
if safe then
    game.walkSmart(safe.x, safe.y, safe.plane)
end

    to — full pathfinder¶

    The original navigation API. Runs the local A* (or StaticPathfinder across regions) and executes the path with hybrid minimap/canvas clicks across multiple ticks. Handles transports automatically.

    • useTransports = true (default): doors, agility shortcuts, fairy rings, manholes, ladders, etc. are invoked as the path crosses them. Set false to force a walk-only path (free accounts, missing quest reqs).
    • Plane is read from the player's current plane — there's no cross-plane API surface, but cross-plane navigation still works via transports.
    • hasArrived() returns true when no walk has been issued yet, or the executor reached PathExecutor::CLOSE_ENOUGH of the goal.
    srs.walk.to(3210, 3210)
-- … later ticks …
if srs.walk.hasArrived() then
    doStuffAtDestination()
end

    Transports (full pathfinder only)¶

    When useTransports = true, the executor handles:

    • Live object-tile resolution. The transport-table origin column is the player STAND tile, not the LocType's actual tile (the object often sits 1 tile off). The walker queries the live scene by object id at fire time so OPLOC1 packets aren't silently rejected.
    • Multi-step transport chains. Manholes (Open → Climb-down), levers-then-doors, and similar two-row entries with the same origin+destination are emitted as a chain. The walker advances through them when it detects the live object's id has flipped to the next step.
    • Recalculation on completion. After any transport (success or timeout), the executor re-plans from the player's actual landing tile.

    If your character genuinely can't use a transport on the shortest route (missing agility level, no Lunar spellbook, etc.) and the pathfinder still tries to route through it, pass useTransports = false to force a walk-only path.

    walkFastCanvas does not invoke transports — it's a one-shot canvas click, so anything more elaborate than "click this tile" needs the full pathfinder.
