    Actions¶

    srs.actions

    Two halves of one problem — did the action I asked for actually happen?

    Half Surface Question it answers
    Pre-dispatch batch / budgetRemaining / pending / cancelAll Can this tick still afford the action, and did each step in my ladder get spent?
    Post-dispatch lastTicket / outcome / info / verify / state Did the action I already spent reach the server, and did it take effect?

    Both halves live in srs::api::Actions (PluginAPI/API/Actions.h in the SDK) and are documented on this page.

    Scripts MUST NOT block

    Verifiers are pumped once per game tick on the script thread, at the top of ScriptEngine::tick() — before your script.onTick runs. Nothing here waits or spins. You fire an action, register a verifier, and read srs.actions.state(handle) whenever you like.

    Why this exists¶

    Across the API a true return means "the click was enqueued", never "the action happened". The Dialogue docs already say this outright; it is equally true of interactions, walks and widget clicks. Three failures live past that return and used to be indistinguishable from success:

    • the per-tick budget gate holds the action so it fires several ticks late, against a world that has moved on;
    • the action is drained, DoAction no-ops, and no packet ever reaches the wire — the "Drop click silently did nothing" bug;
    • the queue is cleared on script stop before the action ran.

    Every script therefore grew its own poll-and-retry ladder. srs.actions replaces them.

    What the engine can and cannot confirm¶

    There is no per-action acknowledgement in the OSRS protocol, and there cannot be one. The outbound action packets carry no request id, sequence number or client token for a reply to reference — OpNpc1 is 4 bytes (index + control), OpLoc1 is 8 (id + x + y + control). A server reply has nothing to name.

    So:

    • sent means "reached the wire", never "the server accepted it."
    • Acceptance is confirmed by observing game state — which is exactly what verify{confirm = ...} is for.
    • The strongest negative signal is the game-message channel, and that is a correlation, not an acknowledgement: a rejection is attributed to the most recent action that reached the wire within a 2-tick window.

    Full write-up: notes/action_confirmation_finding.md.

    Same-tick batching¶

    srs.actions.batch is the pre-dispatch half: it lands several actions inside one game tick, and tells you which ones the tick could not afford.

    local b = srs.actions.batch({
    { "dodge",  function() srs.walk.to(x, y) end },
    { "pray",   function() srs.prayer.setActive(p, true) end,
      tab = srs.tab.PRAYER },
    { "eat",    function() srs.inventory.interactById(food, "Eat") end,
      tab = srs.tab.INVENTORY },
    { "attack", function() srs.npc.attack(boss) end },
}, {
    onDone = function(r)
        if not r.complete then
            for _, e in ipairs(r.missed) do
                print(e.label .. " never fired: " .. e.status)
            end
        end
    end,
})

    Why a ladder needs a runner at all¶

    One action per rendered frame is a hard engine floor, not a pacing preference:

    1. Every scripted action primes a click, and InputSpoofer::stagePendingClick is latest-wins — the engine has one click slot pair.
    2. ClickSlotResetHook consumes at most one staged click per dispatcher tick (~50/s, i.e. once per rendered frame), so at most one CLICK_2 is emitted per frame.
    3. EngineDispatch::drainOnMainThread fires at most one queued action lambda, and only on a CLICK_2.

    So firing two actions in one frame does not get you two actions — the second click overwrites the first, one lambda is left in the paired queue with no click to drain against, and it leaks into a later tick. A frame is ~16 ms and a tick is ~600 ms, so a paced ladder still fits ~30 actions per tick; the real limit is the server's cap, below.

    The per-tick cap, and what a tab switch costs¶

    The server processes at most 8 action-class packets per game cycle (srs.engine.actionLimit()). Over-cap packets are dropped, not queued.

    A sidebar tab switch is one of those 8. Clicking a chrome tab is an ordinary action packet, no different from clicking an item. A ladder that hops prayer → inventory → prayer therefore spends 3 of its 8 slots on sidebar management alone — prefer a resting tab and let the runner coalesce consecutive steps that share one.

    EngineDispatch's own budget gate defers an over-cap action to a later drain. For a tick-scoped ladder that is the wrong answer — the deferred attack lands two ticks late. The batch runner instead fails fast: a step that does not fit is never dispatched, and comes back as gated.

    srs.actions.batch(steps, opts) -> handle¶

    steps is an ordered list. Each entry is a function, or a table:

    Field Meaning
    [1] / label Short name, echoed in the report. Defaults to stepN.
    [2] / fn The action. Return false for "I chose not to act" so the step is not charged a slot; anything else (including no return) counts as dispatched.
    tab Sidebar tab that must be open first, e.g. srs.tab.PRAYER. Omit for "don't care".

    One step = one action packet

    Two clicks inside one fn means the second overwrites the first's staged click and never reaches the server. Split them into two steps.

    opts:

    Field Default Meaning
    tickScoped true Steps still unrun when the tick rolls are dropped and reported expired, rather than fired at a world that has moved on. Set false for ladders that are safe to finish late (bank flows, prep).
    reserve 0 Keep this many action slots free for whatever runs after the batch.
    tabSettleFrames 2 Frames to let the engine draw a newly switched panel before clicking into it. The tab varc flips synchronously, but IfRenderHook's rect snapshot is a frame behind.
    onDone — Called once when the batch retires, with the report.

    The handle has :report(), :done(), :cancel() and .id.

    The report¶

    {
  id = 7, finished = true, complete = false,
  dispatched = 6, noOp = 0, gated = 2, expired = 0, failed = 0, cancelled = 0,
  tabSwitches = 2,
  steps  = { { label = "dodge", status = "dispatched", missed = false, tabCost = 0 }, ... },
  missed = { { label = "attack", status = "gated", missed = true, tabCost = 0 } },
}

    status is one of dispatched, noop, gated, expired, cancelled, failed. missed lists exactly the steps that never reached the wire — that is the list to reprioritise from on the next tick.

    Tabs¶

    If a step names a tab, the runner switches to it, waits for it to read open, waits tabSettleFrames for the panel to be drawn, and only then runs the step. Consecutive steps naming the same tab share one switch. A step already on its tab costs nothing.

    If srs.tab.current() is unreadable (Unknown — the VarClient read is unavailable), the runner does not refuse to act: it switches once blind, settles, and proceeds. Refusing would strand the whole ladder, which is strictly worse than clicking after a switch.

    srs.actions.budgetRemaining(reserve) -> integer¶

    Action slots believed usable this tick. Unlike srs.engine.actionsSentThisTick(), this also counts actions the runner has dispatched whose packets have not reached the wire yet, so it never over-reports capacity.

    srs.actions.pending() -> integer¶

    Batches in flight.

    srs.actions.cancelAll()¶

    Flags every in-flight batch for cancellation. Remaining steps report cancelled. Batches are also dropped automatically when the script that submitted them is disabled or reloaded.

    C++ facade¶

    The batch runner is srs::api::Actions in PluginAPI/API/Actions.h. The Lua handle is sugar over a batch id; in C++ you hold the uint64_t yourself.

    Lua C++
    srs.actions.batch(steps, opts) → handle Actions::submit(ctx, std::vector<ActionStep>, const BatchOptions&) → uint64_t (0 = rejected)
    handle:report() Actions::report(uint64_t id) → BatchReport
    handle:done() !Actions::isRunning(uint64_t id)
    handle:cancel() Actions::cancel(uint64_t id)
    srs.actions.cancelAll() Actions::cancelAll()
    srs.actions.budgetRemaining(reserve) Actions::budgetRemaining(ctx, int32_t reserve = 0) → int32_t
    srs.actions.pending() Actions::pending() → size_t
    — Actions::cancelOwner(uint64_t owner) — drops every batch carrying BatchOptions::owner; how the host tears down a script's in-flight batches on disable / reload

    ActionStep is { std::string label; std::function<bool()> fn; int32_t tab = -1; } (tab takes an InterfaceTab cast to int, -1 for "don't care"). BatchOptions carries tickScoped / reserve / tabSettleFrames plus two fields Lua does not expose: owner (the cancellation token above) and onDone, which fires once on the worker thread under the GIL.

    BatchReport matches the Lua table field-for-field, except that complete is a method (rep.complete()) rather than a field, and it additionally carries tickSubmitted / tickRetired. There is no missed list — filter steps on stepMissed(s.status), which is what the Lua binding does.

    purge, pump and onGameTick are host wiring

    Those three are exported for the client itself (the per-frame pulse lane, the tick rollover, and the lua_State teardown). Plugins and scripts never call them.

    Dispatch tickets¶

    Every marshaled action gets a ticket. Ask for it straight after the call:

    srs.inventory.interactById(id, "Drop")
local t = srs.actions.lastTicket()

    srs.actions.lastTicket() -> integer¶

    Ticket for the most recent action requested on this thread. 0 = the call marshaled nothing.

    srs.actions.outcome(ticket) -> string¶

    Outcome Meaning
    pending queued, not yet drained — the budget gate may be holding it
    sent drained, and an action-class packet went out
    noPacket drained but produced no packet — the silent no-op
    noDispatch the API bailed before anything was queued
    discarded the queue was cleared before it ran (script stop / cancel)
    expired never drained; aged out
    unknown no such ticket, or it fell off the 512-row history

    srs.actions.sent(ticket) -> boolean¶

    outcome == "sent".

    srs.actions.failed(ticket) -> boolean¶

    The action definitively never reached the server. False while still pending, so it is safe to poll.

    srs.actions.info(ticket) -> table | nil¶

    { ticket, outcome, kind, a, b, packets, queuedTicks, ageTicks }
    • kind — "inventory", "widget", "object", "npc", "player", "tile", "clickFire".
    • a / b — kind-specific ids (item id, group/child, npc id + spawn index).
    • packets — action-class packets observed while it ran; 0 = noPacket.
    • queuedTicks — server ticks the budget gate held it before it drained. Non-zero means you queued more actions in a tick than the server's 8-per-tick cap allows and this one landed late.

    srs.actions.recent(n) -> list¶

    Last n ledger rows, oldest first. Returns a proper Lua table.

    srs.actions.queued() -> integer¶

    Ledger tickets enqueued but not yet drained. (Distinct from srs.actions.pending(), which counts batch-runner steps.)

    srs.actions.oldestPendingTicks() -> integer¶

    How long the longest-waiting queued action has been held. A steadily rising number means you are out-running the server's action cap — back off rather than queue more.

    srs.actions.stats() -> table¶

    { opened, sent, noPacket, discarded } — lifetime counters, for HUDs.

    Server rejections¶

    srs.actions.lastRejection() -> table | nil¶

    srs.actions.rejections(n) -> list¶

    { text, reason, ticket, tick }

    reason is a classifier label: materials, space, reach, level, noop, refused. ticket is the correlated action, or 0 when none could own it. Only server/system channels are read — player chat can never be mistaken for a rejection.

    srs.actions.verify(spec) -> handle¶

    Non-blocking poll-and-retry.

    srs.inventory.interactById(id, "Drop")

local h = srs.actions.verify{
    kind    = "drop",
    ticket  = srs.actions.lastTicket(),
    confirm = function() return not srs.inventory.contains(id) end,
    retry   = function() return srs.inventory.interactById(id, "Drop") end,
}

-- later, from onTick:
if srs.actions.state(h) == "failed" then ... end
    Field Default Meaning
    confirm required Truthy = the action took effect. Called once per tick — keep it a cheap state read, never an action.
    retry — Re-dispatch. Called at most attempts - 1 times.
    onDone — Called once with (state, detail) when resolved.
    ticket 0 From lastTicket(). See below — this is what makes the helper better than a hand-rolled timer.
    reject built-in classifier List of server-message substrings meaning "give up now".
    kind "" Label, surfaced in check(h).kind.
    waitTicks 3 Ticks to wait for confirm before retrying.
    attempts 3 Total dispatches allowed, counting the original.

    Pass the ticket. When it resolves noPacket / noDispatch / discarded, the retry fires immediately instead of burning the rest of the waitTicks window waiting for a confirmation that was never coming. A still-pending ticket is not a failure — that is the budget gate holding it.

    Resolution order each tick: confirm → rejection → dispatch outcome → wait window. A confirmed outcome always wins over a rejection guess.

    srs.actions.state(handle) -> string¶

    pending | confirmed | rejected | failed | unknown. Resolved handles stay readable for ~20 ticks, then report unknown.

    srs.actions.done(handle) -> boolean¶

    srs.actions.check(handle) -> table | nil¶

    { state, detail, kind, ticket, attempts, ageTicks }

    detail says why it ended: the rejection text, the dispatch outcome, or "not confirmed within the retry budget".

    Worked example: a bowl craft that the server refuses¶

    The spend is the confirmation — the crafted item sometimes never reads as owned, but the shards always leave.

    local before = srs.inventory.count(shardId)
srs.widget.click(270, 21, "Make")

srs.actions.verify{
    kind      = "make:staff",
    ticket    = srs.actions.lastTicket(),
    confirm   = function() return srs.inventory.count(shardId) <= before - 50 end,
    attempts  = 1,          -- the ladder re-decides next tick; a retry would double-craft
    waitTicks = 8,
    onDone    = function(state, detail)
        if state == "confirmed" then made = true
        else log.info("make " .. state .. ": " .. detail) end
    end,
}

    When the server answers "You do not have the materials required to make that." the verifier resolves rejected on the tick the line arrives — instead of waiting out eight ticks for a spend that was never coming — and the ticket still reads sent, so you can tell "the server refused it" from "the click never landed". Those are different bugs.
