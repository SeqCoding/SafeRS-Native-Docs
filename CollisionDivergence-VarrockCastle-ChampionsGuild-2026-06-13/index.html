    Static collision divergence: Champions' Guild + Varrock Castle doors¶

    Date: 2026-06-13 · Status: root-caused + fixed (bin-level seal) · Areas: Champions' Guild ~(3188–3196, 3352–3364) p0; Varrock Castle keep ~(3203–3224, 3472–3500) p0

    Symptom¶

    StaticPathfinder walk-only routes (useTransports=false) cut straight through the Champions' Guild and Varrock Castle, treating the door tiles as free passages. Live collision blocks the closed doors, so PathExecutor either tries to open them (dragging the player off-route into the building) or detects the door-less gap and flails against the live wall. Observed: a Varrock→Lumbridge walk clipped the guild and produced a 294-step blocked cascade, player stranded ~(3199,3355).

    Unlike the Taverley wall, these are real, permanent buildings with real openable doors — not a spawned-loc cache/live divergence.

    Root cause¶

    Open door edge + missing transport row. These doors are CLOSED-by-default in the live game but appear as walkable edges with no crossing transport in the static map, so A threads through them in both* walk-only and transport mode and the client never issues an "Open door" action.

    How Skretzo/Microbot's data is supposed to model a door (two halves):

    1. a wall (or open edge) in the cache-derived collision-map.zip, and
    2. an Open;Door;<id> row in transports.tsv that provides the crossing when the pathfinder is allowed to open doors.

    RuneLite's collision extractor (which generates Microbot's collision-map.zip) emits no movement-wall flag for an interactType==2 door loc — it leaves the edge OPEN and expects half #2 (the transport row) to carry the crossing. For the doors below, half #2 is missing: there is no transports.tsv row. Result: an always-open edge that nothing gates.

    Evidence¶

    Cache decode (OpenRS2 2593, the live cache) of the door locs, cross-checked against the deployed bin (x64/Release/collision-map.bin, SHA 1067afa6…):

    loc name / action tile(s) p0 edge in transports.tsv? edge in bin
    1805 Door / Open (=closed) (3191,3363) S no OPEN
    11773 Door / Open (=closed) (3195,3357),(3192,3354) +11 in castle W/N/… no OPEN
    32464 Door / Open (=closed) (3222,3491),(3222,3479) S yes (lines 841-844) OPEN→ now sealed
    11772 Door / Close (=open live) (3224,3493) N no already WALL
    15514/15/16 "fai varrock gate" — — no do not exist in cache 2593

    Discriminator — control doors that DO have a transport row are a mix of open and walled edges (9398,32464 OPEN; 12348,12349 WALL), all with a row. So "open door edge" is normal extractor output; the anomaly for 1805/11773 is the missing transport row, leaving the open edge ungated.

    Answers to the three questions¶

    1. Static dump (tools/dump_collision_rect.py over both areas, p0): the building perimeters ARE walled, but the door tiles are open gaps. A canStep flood proves each interior is one connected component with the exterior (guild 44/44 interior tiles exterior-reachable; castle courtyard↔keep↔north all one 1415-tile component). So the buildings are NOT "fully walkable" — the walls are present; only the door edges leak.

    2. Source vs build-script vs door representation. Not the build script: tools/build_collision_map_bin.py only clears bits for explicit --blocked-edges and otherwise copies the zip byte-for-byte. Proof — the deployed bin differs from its pre-seal backup by exactly the 12 edges the local TSV targets (Taverley 5 + palace fence 7), nothing else; and a no---blocked-edges rebuild from the zip is byte-identical (SHA 5cc02d…) to the pre-seal backup. The divergence is in (a) the source collision-map.zip (open door edges, by extractor design) × (b) the door representation (transports.tsv lacks the matching rows). It is NOT a cache-vs-live spawned-loc case (the door locs are real cache geometry).

    3. Are the doors in transports.tsv? No — 1805, 11773, 15514/15516 appear in none of the 24 transport TSVs. 15514/15516 don't even exist as loc defs in cache 2593 (stale IDs); the castle's south courtyard entrance (x3212/3213, y3459) is a permanently open gateway with no gate loc and must stay walkable.

    Fix¶

    Restore the static map's half of the door model: bake the missing wall edges into the bin so walk-only routes around these closed doors (matching live). 16 edges added to tools/collision_blocked_edges_local.tsv, rebuilt into x64/Release/collision-map.bin (new SHA 33eedf58…; prior bin backed up as collision-map.bin.pre-buildings.bak).

    python tools/build_collision_map_bin.py tools/collision-map.zip \
    x64/Release/collision-map.bin \
    --blocked-edges tools/collision_blocked_edges_local.tsv
# -> blocked edges: 28 applied, 6 already blocked, 0 in unmapped regions
    • Champions' Guild (3): 1805 (3191,3363 S) + 11773 (3195,3357 W), (3192,3354 N). Fully encloses the 42-tile interior.
    • Varrock Castle keep (13), plane 0: 11773 ×11 + 32464 ×2. Encloses the 216-tile side-room interior; the great hall stays open (it's a wide archway with no door loc — 174 tiles, correct vs live) and the grounds' south gateway stays open.

    This is the Taverley pattern. Because the seal is baked into the bin (not loaded into TransportRegistry at runtime), it gates only the walking expansion — a future transports.tsv door row would still cross in transport mode (StaticPathfinder transport edges bypass canStep and consult only the runtime registry's blocked set, not the baked bits). So this fix does not foreclose the proper long-term model.

    Not sealed (deliberately)¶

    • Castle south courtyard gateway (x3212/3213, y3459-3470): open in cache, no gate loc. If a closed gate appears live there, it's a spawned/scripted loc — handle via the live-flood blocked-edge bake (Taverley mechanism) after in-game confirmation, not from cache geometry. 15514/15516 are not it.
    • Great hall archway: legitimately open.
    • Upper floors (plane 1/2): 11773 has 11 plane-1 + 3 plane-2 placements (listed by the decode). Add analogously only if walk-only routing on the castle's upper floors is needed; out of scope here.

    Verification¶

    BFS flood with canStep semantics (= what walk-only A* expands), via tools/diag_enclosure.py / tools/diag_door_edges.py / tools/diag_castle.py:

    area before after (rebuilt bin)
    guild interior (44 walkable tiles) all exterior-reachable 42-tile sealed pocket, 0 gap edges
    castle keep side-rooms (390 region tiles) 388 exterior-reachable 216-tile sealed pocket, 0 gap edges (great hall 174 stays open)
    16 door edges all OPEN / canStep=YES all WALL / canStep=no
    whole-bin diff vs pre-build backup — exactly 16 edges OPEN→WALL, nothing else
    no door tile became fully isBlocked — confirmed (each keeps ≥1 open edge)

    A sealed interior pocket is disconnected from the exterior, so no walk-only path (any origin/dest) can route through it — strictly stronger than fixing one route.

    Follow-ups¶

    • Reachability of building interiors: sealing makes walk-only correctly fail to path inside (vs flailing). To enter (e.g. King Roald), add the Open;Door rows to transports.tsv (1805, 11773, and the castle keep doors) AND fix the door-opening walker (it currently drags the player). Then walk-only routes around and transport-mode opens the door — the full model.
    • Confirm doors are closed live: cache "Open" action ⇒ default-closed, and the executor's live block cascade corroborates the guild. A DebugPanel object query on a sealed door tile would confirm each keep door is closed live.
    • Castle south gate: query the south gateway (x3212/3213, y3459-3470) live; if a closed gate spawns, add a Taverley-style live-flood edge.
    • Same failure class elsewhere: any building whose doors lack a transports.tsv row reproduces this. Playbook: dump_collision_rect.py the area → cache-decode the door locs (Open-action = closed) → check transports.tsv → seal the open closed-door edges in collision_blocked_edges_local.tsv → diag_enclosure.py to confirm.
