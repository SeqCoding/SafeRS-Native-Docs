    Static collision divergence: Taverley/Falador border wall¶

    Date: 2026-06-11 · Status: root-caused + fixed (bin-level seal) · Area: ~(2924–2946, 3440–3452) plane 0

    Symptom¶

    StaticPathfinder routed walks from ~(2930,3451) toward the Grand Exchange straight through the Falador north-west (Taverley border) wall with 0 transports. The live game blocks the crossing — there is no door/gate there — so PathExecutor could never traverse it (it survived only via the doorless-gap blacklist after 2 failed probes). The static map showed a one-tile stepped channel through the wall corner: (2941,3444) →E (2942,3444) →S (2942,3443) →E (2943,3443) →S (2943,3442), plus a fully open wall row at x=2924..2935, y=3450|3449 boundary.

    Root cause¶

    The game cache ships an opened-up Taverley border, while the live server still enforces the old closed wall. Specifically, in every cache snapshot checked (OpenRS2 ids 2018 → 2593, i.e. 2025-01-08 → 2026-06-11, XTEA-decoded where needed):

    • The members gate (locs 1727/1728 "Gate", action Open) sits at (2935,3450)+(2935,3451), east edge — the old layout had it one tile east at x=2936 (matches Skretzo's restrictions.tsv "Talvery Gates" and Microbot's "gate at x=2936" comment).
    • The wall row west of the gate (x=2924..2934, y=3449..3451) contains no wall locs at all — open ground in the shipped map squares.
    • The wall corner at (2941..2944, 3442..3445) is built from loc 1911 (wall kit, no actions) and loc 7055 (fence, no actions) where the channel tiles hold only type-1 "wall corner diagonal" trim pieces. Type-1 corners are collision-inert for cardinal movement in the engine (corner flags gate diagonal steps only), and Skretzo's CollisionMapDumper.java does not emit anything for type 1.
    • No multi-state locs are involved: none of 1911/7055/980/1727/1728 has a varbit/varp transform (no opcode 77/92 in their defs). The leagues/broken-wall hypothesis is ruled out.
    • Tile settings (terrain file) carry blocked=1 only on the wall band tiles that are blocked in the static map; the channel tiles are settings=0.

    The live game, however, still blocks the row and the corner channel (user verified live; Microbot's walker users hit the same and hand-patched it on 2026-06-02). Since the closed wall exists in no cache map square, the live server must be re-sealing it with server-spawned locs on zone load — geometry that is invisible to every cache-derived collision dump. The shipped map is presumably the future state of some pending content unlock.

    Answers to the original questions¶

    1. Static dump (2935..2950, 3440..3450 p0): see tools/dump_collision_rect.py output; channel confirmed as the 3-tile pocket {(2942,3444),(2942,3443),(2943,3443)}.
    2. Is collision-map.bin stale? No. The deployed bin was byte-identical (SHA256 3946DE…) to a conversion of Microbot's current collision-map.zip (last regenerated 2026-05-12 from Skretzo's data). Skretzo's upstream zip (regenerated weekly by the ExtractCollisionMap GitHub Action; latest 2026-06-11) contains the identical flags in this region. The build pipeline pins nothing, but no available revision fixes this area.
    3. Multi-state loc? No (see above) — the divergence is cache-vs-live, not a state-resolution choice in the builder.
    4. Rebuild + diff: rebuilt from both current Microbot and current Skretzo zips; region 45_53/46_53 flags unchanged vs deployed. A rebuild alone cannot fix the divergence, hence the exclusion mechanism below.

    Fix¶

    Upstream (Microbot) band-aids this class of gap at search time via blocked_edges.tsv ("Static collision edge overrides for map data gaps"), which our pipeline fetched but never consumed (audit WS: 0 consumers). We now bake those edges into the bin at build time so every consumer of the static map (StaticPathfinder, PathSmoother, goal checks) sees sealed data:

    • tools/build_collision_map_bin.py — new repeatable --blocked-edges FILE.tsv option; clears the corresponding n/e flag bits (blocks are inherently bidirectional in the 2-bit encoding; diagonal edges rejected). Without the option the output is byte-identical to the old builder (regression-verified).
    • tools/collision_blocked_edges_local.tsv — SafeRS-tracked overrides and the only blocked-edges input to the build: upstream's Varrock-fence section (cherry-picked) + 5 edges sealing the corner pocket (not covered upstream). Gate edges stay open on purpose: doors are handled by the walker at execution time.

    Correction (2026-06-11, same day): the first build also imported upstream Microbot's 14 "Taverley wall" row entries (x=2924–2938, y=3450→3449, comment "gate at x=2936"). An in-game object query then showed the live gate at (2935,3450)+(2935,3451) — the cache position, east edge — so the live wall follows the cache's N-S gate line and the ground west of it is open: those row entries are false walls (they shipped alongside Microbot's walker-BFS "false unreachable" bugfix and look like a workaround for that bug, not verified geometry). Removed; do not re-import upstream blocked_edges.tsv wholesale. The corner seal is unaffected: our live flood uses correct per-direction wall bits (CollisionMap.cpp canTraverse), so its "blocked" verdict at the channel reflects real engine flags, not corner-trim misreads. - tools/dump_collision_rect.py — diagnostic dumper (ASCII wall render + per-tile n/e/s/w flags) used throughout.

    Build workflow (after TSV refresh or upstream zip update)¶

    python tools/build_collision_map_bin.py <collision-map.zip> x64/Release/collision-map.bin \
    --blocked-edges tools/collision_blocked_edges_local.tsv

    (Deliberately does NOT pass the fetched upstream blocked_edges.tsv — see the correction above; upstream entries get cherry-picked into the local file after verification.)

    Build log for the deployed bin: blocked edges: 12 applied, 6 already blocked, 0 in unmapped regions over Skretzo's 2026-06-11 zip (deployed SHA256 1067AFA6…, 2664 regions; the unpatched bin remains backed up as collision-map.bin.pre-seal.bak).

    Verification¶

    BFS flood over the bin using canStep semantics from (2930,3451), with the gate door edges cut (incl. diagonal corner-cuts across them):

    bin pocket entered east-side probes (2946,3443)/(2950,3445)/(3000,3450)
    unpatched yes (all 3 tiles) unreachable (pocket exits into the walled yard only)
    patched, gate cut no unreachable — reachable set shrinks by exactly the 3 pocket tiles
    patched, gate open no reachable via the gate + outside corridor only

    So after the seal, the only static crossing of the wall complex is the members gate (a real, openable door), matching live geometry.

    Follow-ups¶

    • Confirm the spawned-loc theory in game: with the client injected, query the live scene objects at (2942,3443)/(2930,3449) and diff against cache — spawned wall pieces should appear that exist in no map square. (DebugPanel object query is sufficient.)
    • Watch for the content flip: if Jagex unlocks the new layout, live will start matching the cache and these 19 edges become an unnecessary (but harmless — the row/corner then sit inside ordinary walls) detour-maker. Re-test with the executor if a Taverley-area game update lands.
    • Same failure class elsewhere: any cache-vs-live spawned-loc area will reproduce this. The playbook: dump_collision_rect.py the area, BFS-trace the leak (verify_seal.py pattern), decode the map square locs vs live, add edges to collision_blocked_edges_local.tsv, rebuild.
