    Pathfinder Audit vs Microbot — 2026-06-10¶

    Verified against current working tree (uncommitted changes incl.) and E:\microbot-audit (clone of 2026-05-27). 41 gaps confirmed, 2 claims refuted. 55 agents, every gap adversarially verified with file:line evidence.

    Pathfinder Improvement Plan — SafeRS vs Microbot Audit Synthesis¶

    Priorities applied in order: SPEED (no idle time) > ACCURACY (exact tile) > COMPLETENESS (every accessible transport). Fixes are grouped into workstreams (WS) because several gaps share one mechanism; every confirmed gap id is mapped to exactly one workstream or the do-not-bother list.

    1. Workstreams (concrete fixes per gap)¶

    WS-A: Run-energy management — speed-no-run-energy-management¶

    The single largest speed lever in the audit (2x walk speed). - Mechanism: Wire the setRunToggle stub (GameSDK/GameData.cpp:214-223) as an IfButton wire packet on the run orb widget (lift widget id from RuneLite per feedback_runelite_data_source, mark kTODO until live-verified), dispatched via EngineDispatch — not Microbot's orb mouse-click. The existing varp-173 reader (getRunToggle, GameData.cpp:207-212) is already correct for state checks. Then add a manageRunEnergy() pass to PathExecutor::onGameTick (Pathfinding/PathExecutor.cpp, near the watchdog block ~:850): enable run when energy > 10 (reader works, GameData.cpp:191-212). - v1.1 — potions: dose stamina/energy/super-energy via Inventory::contains + Inventory::interact when path-remaining >= 20 tiles and energy below a persona threshold. Seed the threshold from the existing MovementProfile FNV-1a char-name infrastructure (project_movement_profile) instead of porting Microbot's mix64 — same behavioral spread (12-24 hardcore / 35-55 casual), zero new seeding code. Enforce the 10s min interval with game-tick counting, not wall-clock sleeps. - Also fix: the stub's false-success return true (GameData.cpp:223) so Player::toggleRunEnergy (PluginAPI/API/Player.cpp:93-97) stops lying to scripts. - Effort: S (toggle + run-on), M (potions). Impact: speed HIGH. Deps: none. Do first.

    4. Do-not-bother list¶

    1. speed-no-bidirectional-search — 2000+ tile single-target requests are rare; the progress-reset budget keeps them alive; high implementation complexity (reverse transport index). No meaningful idle-time win.
    2. speed-visited-hashset-vs-bitset — micro-optimization; reserve(8192) mitigates. Revisit only if WS-C2 telemetry shows worker searches pressing the budget after the underground-wrap fix.
    3. Canoe state machine (part of executor coverage) — largest per-transport verb effort in Microbot's table for routes teleports/fairy rings dominate anyway. Permanently behind a disabled flag.
    4. SEASONAL transports (169 rows) — leagues-only content; irrelevant to production accounts.
    5. Consumable-vs-reusable preference engine (completeness-consumable-preference-absent, second half) — Microbot ships it default-disabled (maxSimilarTransportDistance=0). Do parse the column (E1, one line); don't build filterSimilarTransports' 200-line centroid pruner.
    6. completeness-multi-target-unsupported — real but low: Bank::nearestBank's straight-line guess is usually right, and goal-set termination is easy to add later if AccountBuilder demands it. Not worth scheduling now.
    7. Microbot's ~15-entry object exception table + Motherlode rockfall handler — content-specific patches; add individual entries only when a shipped script hits one.
    8. Full Microbot-parity double-door family components / diagonal corner probes — door v1 + blacklist covers the cost-dominant cases; escalate only if telemetry shows residual door stalls.
    9. Recalc thread pool — thread-per-recalc is fine once F4's cooldown + C1's blacklist bound recalc frequency; cancelFlag already prevents useful-work pileup.
    10. Fail-closed redesign of the collision offset chain — the permissive degradation is a deliberate trade; the cheap health-check alarm (drive-by) plus the existing game-update offset playbook is the right-sized fix.

    Bottom line: Phase 0 is roughly a week of S-effort changes that capture the single largest speed win (run energy), fix two livelock/loop classes (same-goal dedupe, failed-edge memory), and un-defeat the live-collision design — and every later workstream gets safer because of items 4-5. The completeness program (G/H) is exactly the prior roadmap's shape, but the verification moved its first step: the capability gate and failure memory go in before any new transport class, because the audit's most expensive recurring cost is not missing edges — it is edges the executor fires into a 6-second timeout forever.

    Appendix A: Confirmed gaps (full detail)¶

    [critical / speed] speed-no-run-energy-management¶

    No run-energy management — walker never toggles run or doses stamina/energy potions

    Ours: Run handling is completely ABSENT from PathExecutor (zero references). srs::api::Player::toggleRunEnergy exists but delegates to GameData::setRunToggle which is an explicit stub ('needs DoAction wired up'). No automatic run-on at any energy threshold, no potion usage.

    Microbot: manageRunEnergy runs every processWalk pass: enables run when energy>10, doses stamina/energy/super-energy potions when path >=20 tiles remain and energy is below a per-account persona-seeded threshold (FNV-1a(name)^installSeed, 12-24 'hardcore' or 35-55 'casual'), 10s min interval. walkFastCanvas also toggles run.

    Why it matters: Walk speed is literally 2x with run on. A bot that walks (not runs) any fraction of thousands of daily paths pays the single largest time penalty in this entire comparison — dwarfing every recalc/stall optimization. This is also a behavioral fingerprint: real players run.

    Verification (high confidence): Claim is accurate with two minor precision fixes.
