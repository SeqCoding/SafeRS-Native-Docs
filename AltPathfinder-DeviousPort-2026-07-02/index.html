    Alternative Pathfinder — Devious-Client Port: Audit + Design Spec¶

    Date: 2026-07-02 Source audited: C:\Users\Mekkon\Downloads\devious-client-master — net.unethicalite.api.movement (RuneLite fork, "unethicalite"/devious-client) Goal: Add the devious pathfinder as a second, selectable path engine. Both engines stay available behind the existing executor until head-to-head testing picks a winner. Zero changes to any existing srs::api::Walk exported symbol or Lua binding.

    Part 1 — Audit of the devious-client pathfinder¶

    1.1 Search core (Pathfinder.java)¶

    Property Devious SafeRS StaticPathfinder (current)
    Algorithm Unweighted BFS (FIFO, no heuristic) Dual-queue A* (boundary + pending transport queue), Chebyshev heuristic w/ underground y-wrap
    Cost model Uniform 1/tile; transports free; gold tracked ad-hoc for charter ships 1/tile walk, duration ticks per transport, teleport seeding penalty
    Queue LinkedList.remove(0) — O(V²) worst case Proper priority queues
    Visited set HashSet<WorldPoint> (boxed objects, GC-heavy) Packed-int arena
    Cap 5,000,000 visited Progress-reset time budget (5000 ms)
    Failed-edge memory None Session blacklist (excludedEdges)
    Cross-plane goal Implicit (transports carry plane) Explicit goalPlane plumbing (WS-I1)
    Partial-path result None (null on failure) Best-progress partial + found=false

    Verdict on the core: the devious search core is older and weaker than what we already ship. Our StaticPathfinder is a newer Skretzo/Microbot lineage port with a cost model, budget discipline, failure memory, and plane plumbing that devious lacks. Porting the BFS verbatim would be a downgrade. What devious does differently is everything around the search — but note the scoping below: several of those items are already on our own roadmap, so they are reference material for planned work, not engine differentiators.

    1.2 What devious does differently — differentiators vs roadmap accelerants¶

    True engine differentiators (what the A/B test actually decides):

    1. Live-overlay collision with doors-as-open (GlobalCollisionMap.withLocalCollisions() + RegionManager.getTileFlags(), RegionManager.java:313-412). Before searching, devious copies the global static map and overlays the live scene: spawned/despawned objects, wall flags, and — critically — any edge carrying a door with an "Open" action that is not a catalog transport gets its block flag subtracted (RegionManager.java:393-402). The planner paths straight through closed doors; the walker opens them on contact (Walker.handleTransports() diagonal + cardinal door checks, Walker.java:329-379). This is the inverse of our philosophy (static map + execution-time door probe, WS-D1) and directly attacks our known static-vs-live divergence class (project_collision_static_vs_live): cache-vs-live spawned locs and open door-edges without a transports.tsv row.

    2. Event-driven path invalidation (RegionManager subscriptions). Varbit/item-container/widget events set a REFRESH_PATH flag; transportsChanged()/teleportsChanged() diff the transport/teleport sets restricted to the current path and only recalc when something on the route actually changed. Cheaper and more precise than timer-based recalc.

    3. An independent transport dataset (transports.json, 5056 rows verified on disk: source, destination, action, objectId, requirements{quest/item/skill/var/world}; 71 quest, 86 item, 180 skill, 167 world, 243 var requirement uses). Clean JSON schema; maps 1:1 onto our PathfinderConfig account-snapshot evaluation. Running each engine on its own dataset lets the A/B surface data-quality gaps in either catalog.

    Roadmap accelerants — NOT engine differentiators. These looked like devious advantages on first read, but they are already planned for our current implementation (June audit roadmap) and live in the shared executor, so whichever engine wins gets them; they must be excluded from the A/B comparison:

    1. Transport verb coverage via a handler model (TransportLoader.java, 921 lines). Every transport is {source, destination, radii, Runnable handler, Requirements}: object click, NPC interact, NPC-dialog chains, item-use-on-object, fairy-ring dialing, glider/spirit-tree/charter widgets. This is exactly our planned WS-H2 (per-type handler table, fairy rings → NPC boats → spirit trees). Devious's per-category interaction recipes are reference material for that work — executed our way (packets, not widget clicks) — not something the devious engine uniquely provides.

    2. POH teleport layer (TeleportLoader.java POH sections + poh/*.java). Mounted glory/digsite/xeric/mythical cape, jewellery box tiers, portal nexus (varbit-scanned 6672-10103 → HousePortal enum, 30 destinations), house portals. Already planned as Phase 4 POH integration in the June audit roadmap. Devious's varbit maps and destination tables shortcut the data-collection part of that phase; the seeding/execution lands in shared infrastructure both engines consume.

    1.3 Collision data compatibility (important)¶

    Devious's /regions resource (657 KB gzip) is a sparse region map of BitSet4D[64][64][4][2] — 2 bits per tile: walk-north, walk-east, south/west derived from neighbors. This is the same encoding family as our FlagMap/SCM1 collision-map.bin (both descend from Skretzo's data). Consequence: the new engine can consume our existing StaticCollisionMap unchanged — no second collision dataset needed. Optionally, a one-off converter (devious /regions → SCM1) gives us a second dataset for divergence testing, but it is not on the critical path.

    1.4 Flaws found in the devious source (do NOT port)¶

    • LinkedList.remove(0) BFS queue — O(V²); replace with ring buffer.
    • HashSet<WorldPoint> visited — replace with packed-key bitset/arena.
    • Hardcoded NPC/item/widget IDs sprinkled through 900-line TransportLoader switch — brittle across game updates; we keep transports data-driven (TSV/JSON) instead.
    • Gold-cost tracking bolted onto the node struct just for charter ships — model as a currency requirement instead.
    • Reachable.isWalkable() re-floods per call (we already fixed this class with the per-tick cached flood, WS-B3).
    • Wilderness areas hardcoded as WorldAreas in MovementConstants.
    • LocalCollisionMap.blockDoors dead parameter; writeToFile() dead code.
    • Sleeps, widget click chains, camera fiddling in Walker/Movement — superseded by our packet verbs (feedback_packet_path_default, feedback_input_method_priority).
    • Threading trap: devious queries live client state mid-search (LocalCollisionMap → Reachable.getCollisionFlag). Our searches run on a detached worker thread that must never touch engine memory → the live overlay must be snapshotted on the render thread before dispatch (same pattern as refreshUsableTeleports / account snapshot, PathfinderConfig.h threading note).

    1.5 Licensing¶

    BSD 2-Clause (RuneLite base license, inherited by the fork; no per-file headers in the movement package). Compatible with our closed-source distribution: retain the copyright notice + license text in a THIRD_PARTY_NOTICES entry (same treatment as the Skretzo/Microbot-derived collision code). No copyleft obligations.

    Part 2 — Design spec: dual-engine architecture¶

    2.1 Constraints (verified 2026-07-02)¶

    • Frozen surface: srs::api::Walk exported symbols (Walk.h — to 4-arg + 5-arg overloads, state, arrivalDistance, findSafeTile, walkSmart, fastCanvas, cancel, isMoving, hasArrived) and Lua names (game.moveTo/minimapWalkTo/walkTo/walkFastCanvas/walkSmart/cancelWalk/isWalking/hasArrived/walkState). Evolution rule: add overloads / new symbols only (feedback_api_abi_overload_not_default).
    • PathExecutor internals are NOT ABI: ExternalPlugins/include/PluginAPI/IScript.h:31 holds PathExecutor* as an opaque forward declaration; PathExecutor.h does not ship in the SDK. Internal members/methods may be added freely.
    • The producer contract is PathResult (Pathfinder.h:60): path, rawPath, found, cost, nodesExplored, transports[] (PathTransportEdge). Any engine that emits a correct PathResult gets the entire existing executor for free: click dispatch, transport firing, stall recovery, failed-edge memory, run management, telemetry.
    • Worker-thread searches must not read engine memory. All live state is snapshotted on the render thread pre-dispatch.

    2.2 Architecture: engine seam behind the existing executor¶

    One executor, two path producers. We do not build a second walker — the 2,926-line PathExecutor state machine (stall recovery, transport firing, run energy, telemetry) is engine-agnostic already; only path production differs.

                           ┌─ PathEngine::Static (adapter → existing StaticPathfinder, UNTOUCHED)
walkTo(goal, opts) ────┤
                       └─ PathEngine::Devious (new: overlay snapshot + BFS + devious graph)
                                  │
                    both emit PathResult{path, transports[]}
                                  │
                       PathExecutor (existing tick loop, unchanged behavior)

    New interface (new file Pathfinding/IPathEngine.h)¶

    struct PathRequest {
    int startX, startY, startPlane;
    int goalX, goalY, goalPlane;          // goalPlane -1 = start plane
    bool useTransports;
    int budgetMs;
    const std::atomic<bool>* cancelFlag;
    const std::unordered_set<int64_t>* excludedEdges;    // failed-edge memory
    const std::unordered_set<int64_t>* blockedWalkEdges; // quest-locked steps
};

class IPathEngine {
public:
    virtual ~IPathEngine() = default;
    virtual PathResult findPath(const PathRequest&) const = 0;
    virtual const char* name() const = 0;    // "static" / "devious" — telemetry key
    // Render-thread hook, called by dllmain's onGameTick BEFORE any dispatch
    // this tick. Engines snapshot live state here (scene overlay, teleport
    // usability). Static engine: no-op (uses existing refreshUsableTeleports).
    virtual void refreshSnapshot() {}
};
    • StaticPathEngine — ~30-line adapter that forwards PathRequest to the existing StaticPathfinder::findPath(...) signature. StaticPathfinder.h/.cpp are not modified.
    • DeviousPathEngine — the port (see 2.4).

    PathExecutor changes (internal, additive only)¶

    • dispatchStaticPathfinder(...) (PathExecutor.cpp:383) generalizes to dispatchPathfinder(const IPathEngine& engine, ...) — same worker-thread + promise/future + cancel-flag + snapshot pattern, engine call swapped in at PathExecutor.cpp:414. Existing call sites (initial dispatch :255, recalc :373, lookahead :1381) route through the executor's current engine pointer.
    • New appended members: const IPathEngine* m_engineStatic; const IPathEngine* m_engineDevious; const IPathEngine* m_activeEngine; + setEngines(...) late-bind (same pattern as setObjectQuery).
    • New walkTo overload (internal class — overload only for symmetry, not ABI): walkTo(goalX, goalY, useTransports, mode, goalPlane, EngineSelect engine) where EngineSelect { Default, Static, Devious }. Default = the session-level engine set by config/debug panel. Existing 5-param walkTo keeps its exact signature and forwards with Default — all current callers compile and behave identically.
    • Recalc/stall/lookahead re-dispatches use the engine that produced the current path (stored per-walk), so a walk never silently switches engines mid-route.

    Everything downstream is untouched: the transport-fire branch keys off PathTransportEdge.type exactly as today, failed-edge blacklist and telemetry work identically (the blacklist is keyed on packed tiles, engine-independent — a door that times out under one engine is correctly avoided by both).

    2.3 New public API (additive — nothing existing changes)¶

    C++ facade (new exported symbols on srs::api::Walk; existing symbols byte-identical):

    // Walk.h additions
enum class PathEngine { Default = 0, Static = 1, Devious = 2 };

// Same contracts as to(), but pins the path engine for this walk.
static bool toWith(const ScriptContext& ctx, PathEngine engine,
                   int32_t worldX, int32_t worldY, bool useTransports = true);
static bool toWith(const ScriptContext& ctx, PathEngine engine,
                   int32_t worldX, int32_t worldY, bool useTransports, int32_t plane);

// Session default used by to()/walkSmart() when script doesn't pin one.
// Default on startup = Static (current behavior). Sticky until changed.
static void       setEngine(const ScriptContext& ctx, PathEngine engine);
static PathEngine engine(const ScriptContext& ctx);

// Which engine produced the CURRENT/most recent path (for A/B logging).
static PathEngine activePathEngine(const ScriptContext& ctx);

    state(), hasArrived(), arrivalDistance(), cancel(), isMoving() are shared — one executor, one walk at a time — so scripts poll exactly as before regardless of engine.

    Lua (new names only):

    game.walkToAlt(x, y[, useTransports[, plane]])   -- pin Devious engine for this walk
game.setPathEngine("static"|"devious")            -- session default for game.moveTo/walkTo/…
game.pathEngine()                                  -- current session default
game.activePathEngine()                            -- engine of current path ("static"/"devious"/"none")

    Host config: PathfinderConfig gains defaultEngine (init from launcher config / CFG_SAFERS_PATH_ENGINE, default Static), DebugPanel gets an engine dropdown + per-engine telemetry columns. Fail-safe: if DeviousPathEngine failed to init (bad data files), selection silently pins Static and logs once — scripts never break because the alt engine is missing.

    2.4 DeviousPathEngine internals (the port, C++-idiomatic)¶

    New directory OSRSClient/Pathfinding/Devious/:

    File Ports Notes
    DeviousPathEngine.h/.cpp Pathfinder.java BFS with ring-buffer queue (not LinkedList) + packed-int visited arena; termination on goal-area contains; 5M-node cap replaced by the same progress-reset budget our static engine uses (so head-to-head timing is apples-to-apples). Emits PathResult incl. best-effort partial (parity with executor expectations).
    SceneOverlay.h/.cpp withLocalCollisions + RegionManager.getTileFlags Render-thread snapshot (in refreshSnapshot()): copy live 4×104×104 flags from GameSDK/CollisionMap, compute the doors-as-open subtraction (door-action wall/objects not in the transport catalog → clear directional block), diff vs static map, store as a compact override list {packedTile → flagDelta}. Worker thread reads static map + override list only. Cheap: same order of work as the existing per-tick collision copy (WS-B1).
    DeviousTransportGraph.h/.cpp TransportLoader (data part) Loads devious_transports.tsv (converted from transports.json, see 2.5). Indexed by packed origin, same shape as TransportRegistry. Requirements evaluated via the existing PathfinderConfig::isAllowed + account snapshot — no second evaluator.
    DeviousTeleportSeeder.h/.cpp TeleportLoader (data part) Builds the usable-teleport set on the render thread (jewellery, tabs, spells — categories the executor can fire today). Seeds them as start-adjacent edges exactly like our current spell seeding — reuses PathTransportEdge with type discriminant.
    PohModel.h/.cpp (shared, lives in Pathfinding/, not Devious/) poh/*.java HousePortal (30 dests), JewelryBox tiers, nexus varbit map — pure data + varbit reads. This is Phase-4-roadmap data both engines' teleport seeding consumes once POH verbs land; the port merely front-loads the data collection.

    Explicitly not ported: Walker.java / Movement.java execution logic (our PathExecutor supersedes it), Reachable.java floods (WS-B3 flood already better), dialog/widget click chains (packet verbs instead), sleeps/randomized step-size (MovementProfile owns behavioral variance).

    2.5 Data pipeline¶

    • tools/devious_import/convert_transports.py — one-off + re-runnable converter: transports.json (5056 rows) → transports/devious_transports.tsv matching our existing TSV grammar (Origin/Destination/Duration/menuOption/Requirements columns), so Transport::fromTsvRow parses it with zero new parse code. Requirement mapping: questRequirements→Quests, skillRequirements→Skills, itemRequirements→Item IDs, varRequirements→Varbits/Varplayers, worldRequirements→isMembers.
    • Rows that duplicate existing transports.tsv entries are fine — the devious graph is loaded into its own DeviousTransportGraph, so the two engines' datasets stay independent (that independence is part of what we're A/B testing).
    • Optional (deferred): convert_regions.py — devious /regions GZIP → SCM1 for collision-dataset diffing. Not on critical path (encodings are equivalent; we reuse our bin).
    • THIRD_PARTY_NOTICES.md entry: BSD-2-Clause text + devious-client/RuneLite attribution.

    2.6 Executor verb gaps shared by both engines¶

    The devious graph will emit edge types our executor can't fire yet (fairy rings, NPC boats, gliders, spirit trees, POH objects). Two-stage policy, mirroring WS-G2:

    1. Capability gate at graph load (v1): DeviousTransportGraph only admits edge types with a registered executor handler — identical rule to today's static graph. Day one, the devious engine is at verb parity with static; the head-to-head measures search/overlay/data quality, not verb coverage.
    2. Handler table lands verbs for both engines at once (v2, = existing WS-H2 roadmap): per-TransportType handler registry in PathExecutor (fairy rings via IfButton dial packets, NPC boats via OPNPC1 + Resume*Dialog, POH via object clicks in the house instance). Each verb that lands widens both graphs' capability gates simultaneously — the port accelerates WS-H2 by providing devious's per-category interaction recipes as reference, executed our way (packets, not widget clicks).

    2.7 Head-to-head test harness¶

    1. Telemetry split by engine: PathTelemetry counters gain an engine dimension (two instances keyed by IPathEngine::name(); DebugPanel shows side-by-side). Compare: time-to-path, nodes explored, path cost vs actual ticks-to-arrive, recalcs per walk, transport timeouts, unreachables, arrival distance.
    2. Shadow mode (CFG_SAFERS_PATH_SHADOW=1): every dispatch runs both engines on identical PathRequest snapshots (two worker threads — cheap, searches are ms-class). The selected engine's result drives the walk; the shadow result is compared and logged (path cost Δ, length Δ, transports Δ, wall-time Δ, found/partial disagreement) to a CSV under logs/path_ab/. Zero behavioral risk — shadow output never steers.
    3. Route regression suite: Lua script scripts/tests/path_ab_routes.lua walking a fixed route book (bank-to-bank circuits, door-heavy interiors like POH/farmhouses, cross-plane dungeons, teleport-favored long hauls, instance areas) alternating engines, dumping per-route rows. Known weak classes from the June audit (door stalls, plane changes, teleport seeding) get dedicated routes.
    4. Decision gate: after N sessions of shadow CSVs + route-book runs, compare and either (a) promote devious ideas into static (most likely: SceneOverlay + event-driven invalidation are engine-independent modules and can be re-pointed at StaticPathfinder), (b) flip defaultEngine, or (c) delete the loser. The seam makes all three outcomes one-line config changes. Shared-infrastructure work (WS-H2 verbs, POH data) survives the decision either way — it is deliberately kept out of the engines so the A/B verdict never strands it.

    2.8 Phasing & effort¶

    Phase Work Effort Exit criterion
    P0 — Seam IPathEngine, StaticPathEngine adapter, dispatchPathfinder generalization, engine members + EngineSelect, config default S (2-3 d) All existing walks byte-identical via adapter; zero API diff (dumpbin exports compare clean)
    P1 — Data transports.json converter, DeviousTransportGraph, license notice S-M (2-3 d) 5056 rows load; requirement parse coverage report
    P2 — Engine core BFS + visited arena + budget, SceneOverlay snapshot, teleport seeder (spells/items parity first) M (1-1.5 wk) Devious engine produces valid PathResult on route book; executor walks them
    P3 — API + harness Walk::toWith/setEngine exports, Lua bindings, per-engine telemetry, shadow mode, route suite M (3-5 d) Shadow CSVs flowing; A/B dashboard in DebugPanel
    P4 — Engine differentiators Doors-as-open overlay tuning, event-driven invalidation M (3-5 d) Devious engine wins/loses measurably on targeted route classes (door-heavy interiors)
    P5 — Shared roadmap (independent of A/B) WS-H2 handler table (fairy ring → NPC boats → spirit trees) + Phase-4 POH (PohModel data from the port) — widens both engines equally L (amortized) Per-verb live verification; excluded from A/B scoring

    2.9 Risks¶

    • Doors-as-open can strand walks if the walker meets a door it cannot open (quest-locked): mitigated by the existing failed-edge blacklist + blockedWalkEdges (the overlay consults the same session sets before clearing a door edge).
    • Two transport datasets drift — accepted for the A/B period; the decision gate ends it.
    • Shadow-mode thread pressure: two detached search threads per dispatch; bounded by existing cancel-flag discipline; disable shadow by default.
    • Game-update coupling: the port adds no new memory offsets (reuses CollisionMap/VarpSystem/ObjectQuery); update risk is unchanged.
    • PathExecutor churn: all changes additive/appended; header not shipped, so no plugin ABI exposure (verified IScript.h:31 opaque pointer).
